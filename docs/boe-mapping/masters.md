# Masters the mapping depends on

Two layers, and the distinction matters: **reference masters** are facts about
India that are the same for every tenant and are generated from primary sources
into committed TypeScript; **tenant masters** are facts about this CHA's
customers and live in Supabase, maintained by the operator.

## Reference masters — `packages/core/src/masters/`

Generated by `packages/core/scripts/build-masters.py` from
`packages/core/masters-source/`. Regenerate, never hand-edit
`src/masters/generated/`.

### The ICD / gateway port master — already exists

`GENERATED_CUSTOM_HOUSES` carries a `mode` on every station:
`'sea' | 'air' | 'icd' | 'sez' | 'land'`. **No new port master is needed** for
the `L` rule; what was missing was the code that reads it. Examples:

| Code | Name | mode | Transport mode it implies |
|---|---|---|---|
| `INNSA1` | Nhava Sheva Sea | `sea` | `S` |
| `INTKD6` | ICD Tughlakabad | `icd` | `L` |
| `INSNF6` | ICD Sanand | `icd` | `L` |
| `INBOM4` | Sahar Air Cargo | `air` | `A` |
| `INATQ4` | Attari Road (land customs) | `land` | `L` |

### The Exim scheme directory — two sources, kept apart

`EXIM_SCHEME` is the ICES Scheme Code directory, transcribed from
`data/customs-corpus/icegate-specs/ICES 1 5 Customs - DGFT Message Formats
Version 1 9 (21 07 08).pdf`. It was previously transcribed from a photograph of
the Logi-Sys dropdown that happened to be scrolled, which stopped it at `20` and
cost three of the four licence jobs in the corpus their whole workbook.

`VENDOR_EXIM_SCHEME` holds codes Logi-Sys writes that are in **no** published
directory, each carrying the vendor export that proves it: `32` (Tariff Rate
Quota, `ex_job27`) and `RD` (RoDTEP scrip, `ex_job20`) — both schemes postdate
the 2008 directory. Kept as a separate map so "the ICES directory says so" and
"we have seen Logi-Sys do it" do not become the same claim. An unknown code is
still refused; "unknown" now means *in neither source*.

`resolveIndianStation(place)` matches a free-text place of delivery off a bill
of lading to one of these rows. Matching order: exact ICES code → normalised
exact name → `ICD <PLACE>` / `<PLACE> ICD` / `CFS <PLACE>` forms → unique
substring. Ambiguity resolves to nothing and warns, rather than picking.

## Tenant masters — Supabase

### `organizations` — the importer master

Already exists (`supabase/migrations/20260822000001_organizations.sql`),
populated by uploading the Logi-Sys **Organization Repository** export
(`apps/web/lib/org-repository.ts`). One row per party **per branch**, carrying
`name`, `branch_name`, `branch_sr_no`, `ad_code`, `iec`, `pan`, `gstin`,
address and the role flags.

Columns added for GENERAL:

| Column | Type | Feeds | Maintained by |
|---|---|---|---|
| `aeo_status` | `none` / `T1` / `T2` / `T3` | `DutyPaymentStatus_T_D` | operator |
| `aeo_certificate_no` | text | evidence for the above | operator |
| `aeo_valid_till` | date | expired AEO stops qualifying for `D` | operator |
| `importer_ref_required` | boolean | `Importer_RefNo` | operator |
| `default_custom_house` | text (ICES code) | `CustomsHouseCode` fallback | operator |

Columns added for INVOICES, beside the `marine_open_policy_rate_percent` that
already fed the insurance rate:

| Column | Type | Feeds | Maintained by |
|---|---|---|---|
| `marine_policy_no` | text | named in the over-insurance warning | operator |
| `marine_policy_sum_insured_inr` | numeric | the policy total | operator |
| `marine_policy_per_sending_limit_inr` | numeric | **the check**: a consignment worth more than this is over-shipped against the cover | operator |
| `marine_policy_valid_till` | date | an expired policy is not cover | operator |

The rate says what the premium costs; none of it says what the policy covers,
and the customer's rule for the insurance column is that a consignment must not
exceed the sum insured. `checkSumInsured()` in `apps/web/lib/parties.ts` totals
the declared value across every invoice and raises an `error` flag naming the
shortfall — see [05-invoices.md §6](05-invoices.md#6-ins_--ins_amount--ins_currency).

> DGFT / IEC API: not used. The importer master is the Logi-Sys organization
> repository plus the operator-maintained columns above — the same repository
> Logi-Sys itself resolves parties against, which is the only thing that makes
> the `Importer` / `Branch Name` / `AD_Code` triple match on upload. Fetching a
> second, differently-spelled copy of the party from DGFT would break that.

### `organization_ad_codes` — new

An importer banking through more than one AD code. One row per code; the
organization's own `ad_code` remains the default.

| Column | Notes |
|---|---|
| `organization_id` | the importer |
| `ad_code` | 7 digits, **text** — `0510226` loses its leading zero as a number |
| `bank_name`, `branch` | so the operator can tell them apart |
| `is_default` | at most one per organization |

When an importer has more than one and the job has not chosen, `AD_Code` is a
**blocker**, not a guess.

### `job_boe_header` — new

Everything on GENERAL a person decides or keys, one row per job. This is the
operator layer of the precedence chain, and it always wins.

| Column | Feeds |
|---|---|
| `transport_mode`, `customs_house_code`, `be_type`, `duty_payment_status` | overrides for columns 1, 2, 3, 12 |
| `ad_code`, `importer_ref_no` | columns 6, 7 |
| `igm_no`, `igm_date`, `inward_date`, `be_filing_date` | columns 13, 14, 15 |
| `filing_status` | override for column 13 |
| `is_first_check`, `is_green_channel`, `is_kachcha_be`, `is_hss`, `is_bonds_certificates`, `is_transhipment`, `itc_lic_details`, `is_under_provisional_assessment` | columns 16–23 |
| `is_under_sec46`, `is_under_sec48` | override for the derived flags 14, 15 |
| `warehouse_code`, `inbond_be_no`, `inbond_be_date`, `bond_no`, `bond_date`, `bond_expiry_date` | INBOND_EXBOND 1–12 |
| `is_warehouse_sale`, `is_sec65_manufacturing_wh` | INBOND_EXBOND 13–14 |
| `exbond_clearance_kind` | gates SEC65_EXBOND_INFO — only `resultant_product` declares finished goods |
| `released_packages`, `released_package_code`, `released_gross_weight_kg`, `released_uom` | the ex-bond release, which reaches SHIPMENT and ITEMS |
| `sec46_override_reason` | why a derived flag was cleared (holidays, waiver granted) |
| `line_no` | SHIPMENT 6 — the IGM line number, same ICEGATE enquiry as `igm_no` |
| `gateway_igm_no`, `gateway_igm_date`, `gateway_inward_date` | SHIPMENT 21–23 — the gateway sea port's manifest, on an inland (ICD) filing only |
| `package_unit_code` | SHIPMENT 14, when no document names the package kind — which is every air job |
| `marks_and_nos` | SHIPMENT 19, when the BE declares something other than `AS PER BL` |

Despite the section title, the last six are SHIPMENT's, not GENERAL's. They live
here because they are keyed on the same screen at the same moment: an operator
looking up an IGM on ICEGATE has the line number and the gateway manifest in
front of them, and splitting the table would split one lookup across two forms.

### `bonded_warehouses` — new

A cache of customs bonded warehouses, keyed by the eight-character code. Public
data, cached rather than fetched, because a government portal must not sit in
the path of a workbook download.

| Column | Source | Notes |
|---|---|---|
| `code` | the job | 8 chars, unique per company, stored upper-case |
| `name`, `address1`, `address2`, `city`, `pin` | ICEGATE, else operator | not encoded in the code — nothing can infer them |
| `country` | constant `IN` | a warehouse under the Customs Act is in India |
| `station_code`, `warehouse_type` | the code itself | derived offline, cached for querying |
| `source` | `icegate` / `operator` / `document` | how the name and address were obtained |
| `is_sec65`, `sec65_permission_no`, `sec65_permission_date` | the MOOWR permission, via the operator | not in the code and not on ICEGATE's enquiry; defaults `INBOND_EXBOND.IsSEC65ManufacturingWH` |

**The code decodes with no network**: `MAA1U001` = `MAA1` (→ `INMAA1`, Chennai
Sea) + `U` (public, s.57) + `001`. `parseWarehouseCode()` in
`packages/core/src/masters/warehouse-code.ts` validates the port prefix against
`GENERATED_CUSTOM_HOUSES`, so a code naming no real station is caught before
Customs sees it.

**ICEGATE's public warehouse enquiry** —
`enquiry.icegate.gov.in/enquiryatices/wareHouseCodeEnquiry`, no login and no
captcha, takes a code or a name and returns code / name / address (ICEGATE 2.0
Public Enquiries user manual v1.01, §5.5). The host is India-only; see
[open-questions.md](open-questions.md#the-icegate-warehouse-enquiry-endpoint).

### `job_sec65_finished_goods` — new

The products a Section 65 ex-bond clearance is actually selling, one row per
(GST invoice × finished product). A child table of the job rather than columns
on `job_boe_header`, because an item can feed several GST invoices — ICES's own
note on Control Slno is *"An Item can have Multiple GST Invoice"* — and one GST
invoice can consume several items.

| Column | Feeds |
|---|---|
| `seq` | the declaration order, which is what Logi-Sys numbers Control Slno from |
| `gst_invoice_no`, `gst_invoice_date` | SEC65_EXBOND_INFO 3–4 |
| `finished_cth`, `finished_desc` | SEC65_EXBOND_INFO 5–6 — the **finished** product's heading, not any input's |
| `finished_qty`, `finished_uqc` | SEC65_EXBOND_INFO 7–8 |
| `applies_to_items` | which item serials the entry declares against; `null` is every item |
| `source` | `operator`, or `document` when proposed off an attached `gst_tax_invoice` |

Contract: [08-sec65-exbond-info.md](08-sec65-exbond-info.md).

### `supplier_relationships` — new

Whether one of this CHA's importers is related to one of its suppliers, and
under what Special Valuation Branch order. Keyed on the **pair**, because that
is what an SVB order covers: the same overseas seller can be related to one
importer and at arm's length from another, so these columns cannot hang off the
supplier's own row.

| Column | Feeds |
|---|---|
| `is_related` | `INVOICES.Is_Related`, and `Relation` (the literal `YES`) |
| `base`, `condition` | `INVOICES.Base` / `.Condition` — blank unless related |
| `svb_ref_no`, `svb_date` | `INVOICES.SVB_Ref_No` / `.SVB_Date` |
| `svb_custom_house` | `INVOICES.Custom_House_Code` — the house that imposed the load, **not** the filing station |
| `svb_loading_basis` | `INVOICES.SVB_Loading_Basis` — `A` or blank |
| `svb_rate_assessable`, `svb_status_assessable` | `INVOICES.SVB_Rate_Assessable` / `.SVB_Status_Assessable` (`F`/`P`) |
| `svb_rate_duty`, `svb_status_duty` | the same pair on duty |
| `revenue_deposit_percent` | `INVOICES.RD_%`, which is enabled only on a related pair |

A database constraint refuses `base`, `condition` or a deposit on a pair that is
not related — those three qualify a relationship, and recording them without one
is a contradiction rather than a detail.

Read by `applySupplierRelationship()` in `apps/web/lib/parties.ts`, once both
parties are bound. **No record means nobody has said**, which is not the same as
a record saying no — `Is_Related` used to be the constant `N` on every Bill of
Entry, which is a declaration to Customs.

## `product_master` — the importer's confirmed products

One row per importer + normalised description (`productDescriptionKey`):
CTH, general description, brand, model, end use, Exim scheme, and the
notification choices a person made. Written when the operator confirms a line
on the job's items panel (`rememberProduct` in `apps/web/lib/items.ts`); read
on every draft rebuild by `applyItemResolution`. A hit clears the "confirm
classification" blocker for that line. Replaces the filesystem job memory
(`data/masters/product-memory.json`), which only `/legacy` wrote.

## `job_items` — the operator's edits to a job's lines

Partial `DraftItem` per invoice/item serial, applied over the draft after every
re-read, the same layer `job_containers` is for CONTAINERS.
